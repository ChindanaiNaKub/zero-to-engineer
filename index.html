Read less. Recall more.

Six mechanisms with evidence behind them. Each one is wired into a control on this page, not printed as advice.

  1. 01

    Answer before you look

    Every gate asks you to recall before its answer is available. Rereading raises confidence without raising retention.

    Roediger and Karpicke (2006), Dunlosky et al. (2013). Sources 1 and 2.

  2. 02

    Come back on a schedule

    Passed questions return in 1, 3, 7, 14, 30, 60 and 120 days, mixed across levels rather than blocked by topic.

    Cepeda et al. (2006), Cepeda et al. (2008). Sources 3 and 4.

  3. 03

    Advance on a criterion

    A level passes at 80 percent on its gate. Time spent is not the measure; the criterion is fixed and visible.

    Bloom (1968), Bloom (1984). Sources 5 and 6.

  4. 04

    Study one, finish one, do one cold

    Each level has three rungs. One language and one stack all the way through keep extraneous load down.

    Sweller (1988), Sweller et al. (1998), Atkinson et al. (2000). Sources 7 to 9.

  5. 05

    Work just past your edge

    The capstone is one task you cannot quite do yet, with a check you can run yourself. Feedback arrives from the artifact.

    Ericsson, Krampe and Tesch-Romer (1993). Source 10.

  6. 06

    Predict, then compare

    Guess your gate score before you begin. The gap between guess and result is the one number that corrects overconfidence.

    Chi et al. (1994), Bjork (1994), Dunlosky et al. (2013). Sources 11, 12 and 2.

Two mechanisms here have promising but thinner evidence: interleaved review and self-explanation. Dunlosky et al. rate them moderate rather than high utility. They cost little, so they stay. What is deliberately absent: video lectures, streaks, badges, a leaderboard, an account and a backend. None of them improve retention, and each adds code. This is a map and a scheduler, not a course. Gates are self-graded, so a pass means you were honest, not that a machine checked you. The hour budgets below are planning estimates, not measurements. L10 has no finish line.

Eleven levels, one ladder

The order follows dependency, not popularity. Each level exists because the next one cannot be understood without it.

Read a level, work its three rungs, build the capstone, then take the gate. If you already know a level, take the gate anyway. A miss is information, not a failure.

Rough budget across all eleven levels: 900 to 1,200 focused hours, plus real projects. Mastery is a practice, not a certificate.

Ground L0 to L2

L0The machine and the learner15-25 hNot started

A computer transforms symbols by following explicit instructions. Every layer above it is an abstraction built to hide that fact, never to change it.

What you must know

Bits and addresses
All data is numbers. Memory is a numbered array of bytes; a file is a named sequence of them.
The fetch loop
A processor fetches, decodes and executes one instruction after another. A program is data that another program reads as instructions.
Layers of verbs
Hardware, kernel, process, runtime, interpreter. Each layer offers fewer, safer verbs than the one below.
The shell
A shell starts other programs. Paths, arguments, standard input and standard output are its whole vocabulary.
Encoding
Characters are numbers agreed by a table. Bytes mean nothing until a reader interprets them.
How learning works
Recall before review, space the reviews, predict your score. Familiarity from rereading is a poor signal.

Practice ladder

  1. Study one. Trace python hello.py on paper: disk, process, interpreter, system call, pixels. Write each step in your own words.
  2. Finish one. A half-filled trace of cat notes.txt > out.txt is given. Fill in where bytes come from and where they go.
  3. Do one cold. Without notes, explain why a text file can hold a picture and why a program can be data.

Build thisA working toolchain: editor, shell, interpreter, Git. A one-page account of how a program runs, written from memory, plus a dated learning log.

Gate, four questions

Answer from memory before opening any answer. Set a prediction first, then grade each question honestly.

  1. What does a processor do, in one sentence?

    Reveal the answer

    It repeatedly fetches an instruction, decodes it, executes it and advances. Everything above is a layer over that loop.

  2. Why is a file only bytes until something reads it?

    Reveal the answer

    Bytes carry no type or meaning. An encoding and a program agree on how to interpret them.

  3. Name the layers between a keypress and your code running.

    Reveal the answer

    Hardware, kernel, shell or process, runtime or interpreter, your code. Any correct chain that keeps the idea of layers counts.

  4. Why does rereading feel effective but fail?

    Reveal the answer

    It raises familiarity and confidence without exercising retrieval. Only attempts to recall strengthen later recall.

Go deeper

  • Code: The Hidden Language of Computer Hardware and Software, Charles Petzold Build a computer from switches upward.
  • MIT The Missing Semester of Your CS Education Shell, Git and tooling in eleven free lectures.
  • Harvard CS50x, week 0 A gentle first week on bits and algorithms. Free.
  • Computer Science Distilled, Wladston Ferreira Filho A short map of the whole field first.

L1Programming primitives60-80 hNot started

Every program is data plus three forms of control: sequence, choice and repetition. A function is only a named, reusable piece of that control.

What you must know

Values and types
A value has a type. The type fixes which operations are legal before the program runs.
Names and state
A name refers to a value. Assignment changes the reference, not the value it used to hold.
Choice and repetition
A conditional selects a path. A loop repeats while an invariant still holds.
Functions
A function maps inputs to an output plus possible effects. Make the effects visible in its name.
Collections
Lists, maps and strings are one idea: many values under one name with rules for access.
Reading errors
A traceback is evidence, not noise. Read it from the bottom up, form one hypothesis, then test it.

Practice ladder

  1. Study one. Read a worked solution to a small problem, then say what each line changes.
  2. Finish one. The same problem with three lines removed. Fill them without running the code first.
  3. Do one cold. Solve a new small problem from an empty file. Check only after you commit to an answer.

Build thisA command line tool that reads a file and transforms it, for example a word counter or a plain text task list. No framework, no libraries beyond the standard library.

Gate, four questions

Answer from memory before opening any answer. Set a prediction first, then grade each question honestly.

  1. Name the three forms of control flow.

    Reveal the answer

    Sequence, selection and iteration. Every imperative language offers these three.

  2. What does a function hide?

    Reveal the answer

    A body of control and data behind a name and a signature. Callers need the contract, not the body.

  3. Why is a traceback read from the bottom?

    Reveal the answer

    The last frame is where the failure surfaced; the frames above are the chain of calls that led there.

  4. What is the difference between a value and a name?

    Reveal the answer

    A value is the data. A name is a binding that currently refers to it and can be rebound.

Go deeper

  • Think Python, Allen Downey Free, and it teaches the ideas rather than the syntax.
  • CS50’s Introduction to Programming with Python Free, with graded problem sets.
  • Automate the Boring Stuff with Python, Al Sweigart Free online. Practice on real files.
  • How to Design Programs, Felleisen et al. Read for the design recipe, not the language.

L2Data, algorithms and cost70-90 hNot started

The cost of a computation is a property of the data structure, not the language. Choose the structure that makes the operation you need cheap.

What you must know

Contiguous versus linked
An array gives constant-time indexing and costly inserts. A linked list gives cheap inserts and linear lookup.
Hash tables
A hash function trades a little space and some collisions for near constant time lookup.
Trees
A tree turns a linear search into a logarithmic one by keeping order in the shape.
Recursion and invariants
A recursive function is a proof by induction. State the invariant before you write the case.
Big-O
Count growth in the input size, not seconds. Drop constants, keep the dominant term.
Memory hierarchy
Cache, RAM and disk differ by orders of magnitude. Locality often beats a better algorithm.

Practice ladder

  1. Study one. Trace binary search on sixteen sorted values, writing the invariant at each step.
  2. Finish one. A partly written hash table with get missing. Implement it and explain collisions.
  3. Do one cold. Given a workload of one million inserts and one million lookups, pick a structure and defend it with a measurement.

Build thisImplement an array list, a hash map and a binary search tree from scratch. Benchmark insert and lookup at four input sizes and write down where each one wins.

Gate, four questions

Answer from memory before opening any answer. Set a prediction first, then grade each question honestly.

  1. Why is array indexing constant time?

    Reveal the answer

    The address is base plus index times element size, computed directly, independent of n.

  2. What does a hash table trade for fast lookup?

    Reveal the answer

    Extra space and the cost of handling collisions, plus a hash function that spreads keys evenly.

  3. What must be true before each step of binary search?

    Reveal the answer

    The target, if present, lies inside the remaining sorted interval. Each halving preserves that invariant.

  4. Why can a theoretically slower algorithm win on real hardware?

    Reveal the answer

    Constant factors and cache locality dominate at realistic sizes. Big-O describes growth, not wall time.

Go deeper

  • Grokking Algorithms, Aditya Bhargava Pictures first, then the maths.
  • Algorithms, Sedgewick and Wayne, course site Free code, lectures and exercises.
  • VisuAlgo Step through a structure until you can predict the next move.
  • Introduction to Algorithms, Cormen, Leiserson, Rivest and Stein Use as a reference, not a cover-to-cover read.

Craft L3 to L5

L3Abstraction and design60-80 hNot started

Complexity is controlled by giving each part one job and one stable interface. The interface is the contract; the implementation is a secret.

What you must know

Information hiding
Decompose around decisions likely to change, so each secret lives in one module. Parnas, 1972.
Deep modules
A small interface over a lot of behavior beats many shallow parts. Prefer fewer, deeper modules.
Cohesion and coupling
Keep things that change together close. Keep things that change independently apart.
Naming
A name is the first and cheapest abstraction. It should say what the thing does, not how.
Pure and effectful
Separate computation from I/O. A pure function can be tested and reasoned about alone.
Errors as contract
What a function rejects and what it raises are part of its interface, not an afterthought.

Practice ladder

  1. Study one. Read a 400-line script and mark every place a decision about file format leaks out.
  2. Finish one. A refactor with the module boundaries drawn and two bodies left blank. Fill them.
  3. Do one cold. Take a fresh messy script and restructure it without hints, then compare the two designs.

Build thisRefactor a deliberately messy program into modules with a documented interface, a test suite and a short README that states each contract. Write one page on what you hid and why.

Gate, four questions

Answer from memory before opening any answer. Set a prediction first, then grade each question honestly.

  1. What is the criterion for splitting a system into modules?

    Reveal the answer

    Hide design decisions likely to change, so a change touches one module instead of many.

  2. Why is a deep module cheaper than a shallow one?

    Reveal the answer

    Callers learn one interface and get a lot of behavior; shallow modules multiply interfaces without removing complexity.

  3. What belongs in an interface contract?

    Reveal the answer

    Inputs, outputs, preconditions, postconditions and the errors it can raise.

  4. Why keep I/O at the edge?

    Reveal the answer

    Pure core logic is deterministic, composable and testable; effects are where most surprises live.

Go deeper

  • A Philosophy of Software Design, John Ousterhout The clearest short book on complexity.
  • On the Criteria To Be Used in Decomposing Systems into Modules, D. L. Parnas (1972) The original argument for information hiding.
  • Structure and Interpretation of Computer Programs, MIT OCW Abstraction built from the ground up. Free.
  • The Pragmatic Programmer, Hunt and Thomas Habits of a working developer.

L4Correctness60-80 hNot started

You cannot establish correctness by reading code. State the expected behavior first, then build a mechanism that fails when the behavior is wrong.

What you must know

Tests as specification
A test is a claim about behavior, written so a machine can check it forever.
Unit, integration, property
Unit checks a part. Integration checks a seam. Property checks a law over many inputs.
Invariants
Write down what must always be true, then make the program check it while it runs.
Debugging as experiment
One hypothesis, one change, one observation. Bisect the search space instead of guessing.
Mutation and fuzzing
Break the code on purpose to see whether the tests notice. Generate inputs instead of imagining them.
Types and coverage
A type checker is a cheap proof of some claims. Coverage tells you what ran, not what was checked.

Practice ladder

  1. Study one. Read a test suite and, for each test, write the behavioral claim it encodes.
  2. Finish one. A suite with two property tests left as TODO. State the invariant and implement them.
  3. Do one cold. Given a library with five seeded bugs, find all five using only failing tests and a bisect.

Build thisAdd unit and property-based tests to your L3 library. Run mutation testing until at least four of five mutants are killed. Fix every bug the tests find and record which test caught each one.

Gate, four questions

Answer from memory before opening any answer. Set a prediction first, then grade each question honestly.

  1. Why is a test a specification, not just a check?

    Reveal the answer

    It states expected behavior in executable form, so later changes are judged against a written claim.

  2. What does a property-based test add over an example?

    Reveal the answer

    It checks a law across hundreds of generated inputs, including cases you would not have written by hand.

  3. Why is high coverage weak evidence of correctness?

    Reveal the answer

    It counts executed lines, not asserted behavior. A line can run with no meaningful check attached.

  4. What is the loop for debugging?

    Reveal the answer

    State a hypothesis, make one change that distinguishes it, observe the result, then narrow the search.

Go deeper

  • The Fuzzing Book, Zeller et al. Free, executable chapters on generating tests.
  • Hypothesis documentation Property-based testing in Python, with examples.
  • Working Effectively with Legacy Code, Michael Feathers How to get untested code under test safely.
  • Google Testing Blog Short, evidence-led essays on test practice.

L5Systems and the machine80-100 hNot started

Program behavior emerges from hardware, the operating system and the runtime. Time, memory and I/O are budgets, not abstractions.

What you must know

Processes and threads
A process owns an address space. Threads share one, which is where races come from.
Virtual memory
Your pointers are addresses in a map maintained by the kernel, not physical locations.
Stack, heap, cache
Allocation site decides lifetime. Locality decides speed more than instruction count.
System calls
Every file, socket and clock reading crosses into the kernel. That crossing costs.
Networking
TCP gives an ordered byte stream, not messages. HTTP is a convention on top of it.
Profiling
Measure where time goes before changing anything. Guessing at bottlenecks is wasted work.

Practice ladder

  1. Study one. Read a strace of a small program and label each syscall with what the code was doing.
  2. Finish one. A server that handles one client. Add a thread pool and complete the locking.
  3. Do one cold. Build a concurrent echo server, then find the race with a stress test.

Build thisA concurrent TCP server with a documented protocol. Measure throughput and tail latency at 1, 10 and 100 clients, find one race, profile one hot path, and write a one-page report with the numbers you measured.

Gate, four questions

Answer from memory before opening any answer. Set a prediction first, then grade each question honestly.

  1. Why do shared-memory threads race?

    Reveal the answer

    Threads share an address space, so interleaved reads and writes to one location depend on scheduling, not on source order.

  2. What does virtual memory buy you?

    Reveal the answer

    Isolation between processes, a simple contiguous address space, and the ability to back memory with disk.

  3. Why is TCP a byte stream, not a message protocol?

    Reveal the answer

    It preserves order and reliability but not boundaries; the receiver must frame messages itself.

  4. Why profile before optimising?

    Reveal the answer

    Time concentrates in a small part of a program, and intuition about where is usually wrong.

Go deeper

  • Computer Systems: A Programmer’s Perspective, Bryant and O’Hallaron The standard bridge from code to hardware.
  • Operating Systems: Three Easy Pieces, Arpaci-Dusseau Free textbook: virtualisation, concurrency, persistence.
  • Beej’s Guide to Network Programming Free, plain-spoken sockets from scratch.
  • The Linux Programming Interface, Michael Kerrisk The reference for syscalls when you need the detail.

Systems L6 to L8

L6Data and persistent state60-80 hNot started

Model data around the questions you must answer. A database is a trade between how fast you can ask, how safely you can write, and how much consistency you can afford.

What you must know

The relational model
Tables, keys and joins. Normalise to remove contradictory facts, denormalise only with a measured reason.
Indexes
An index is a second, ordered copy of some columns. It speeds reads and slows writes.
Query plans
EXPLAIN shows the algorithm the database chose. Read it before adding an index.
Transactions
ACID is a promise about failure and concurrency, not a speed setting.
Isolation
Each level trades anomalies for throughput. Know which anomaly your application can tolerate.
Replication
Copies buy availability and read scale; they also buy stale reads and harder writes.

Practice ladder

  1. Study one. Read an EXPLAIN plan for a slow join and name the operation that dominates.
  2. Finish one. A schema with two tables and a missing foreign key. Add the constraint and the migration.
  3. Do one cold. Given a slow query and a million rows, get it under a target time with one change.

Build thisDesign a schema for a small application, load a million rows, take one query from over a second to under fifty milliseconds using EXPLAIN and an index, then write and rehearse a backup and restore.

Gate, four questions

Answer from memory before opening any answer. Set a prediction first, then grade each question honestly.

  1. Why does an index speed reads but slow writes?

    Reveal the answer

    It keeps an extra ordered structure that must be updated on every insert, update and delete.

  2. What does ACID promise?

    Reveal the answer

    Atomicity, consistency, isolation and durability: a transaction either fully applies or not at all, and a committed result survives failure.

  3. Why is a normalised schema easier to keep correct?

    Reveal the answer

    Each fact lives in one place, so an update cannot leave two copies disagreeing.

  4. Why does CAP not simply mean choose two?

    Reveal the answer

    It describes behavior during a network partition; most systems tune per-operation consistency and availability rather than picking once.

Go deeper

  • Use The Index, Luke! Free, focused on how indexes actually behave.
  • CMU 15-445/645 Database Systems Free lectures and a build-a-database project.
  • PostgreSQL documentation Read the concurrency and performance chapters first.
  • Designing Data-Intensive Applications, Martin Kleppmann The trade-offs behind storage and replication.

L7Architecture and design decisions80-100 hNot started

Architecture is the set of decisions that are expensive to reverse. Delay them until you have evidence, then isolate each one behind a boundary.

What you must know

Requirements first
Write down what must be true. A boundary drawn before that is a guess.
Domain model
Name the concepts the business uses and make the code speak the same language.
Ports and adapters
Put the decision at the edge. The core should not know which database or queue exists.
Synchronous versus events
A call needs an answer now. An event records that something happened. Pick deliberately.
ADRs
One page per decision: context, options, choice, consequences. Written when you decide.
Reversibility
Prefer the option you can undo. The cost of a decision is the cost of changing it later.

Practice ladder

  1. Study one. Read a published design doc and list each decision and what would make it wrong.
  2. Finish one. A design doc with the options filled in and the choice left blank. Choose and justify.
  3. Do one cold. Write an ADR for a real choice in your own project, then try to argue the opposite.

Build thisA design document and a working system of at least three components with clear boundaries, one asynchronous path and three ADRs. Include a C4 container diagram and a table of the trade-offs you rejected.

Gate, four questions

Answer from memory before opening any answer. Set a prediction first, then grade each question honestly.

  1. What makes a decision architectural?

    Reveal the answer

    It is expensive to reverse and shapes many later decisions; cheap, local choices are not architecture.

  2. Why write an ADR at decision time?

    Reveal the answer

    The context and rejected options are still known then, and later readers need the why, not only the what.

  3. What does a hexagonal boundary protect?

    Reveal the answer

    Domain logic from the details of delivery and storage, so either can change without rewriting the core.

  4. Why prefer a reversible choice?

    Reveal the answer

    It keeps the option to learn, and learning is worth more than being right early under uncertainty.

Go deeper

  • Designing Data-Intensive Applications, Martin Kleppmann Trade-offs, not recipes.
  • C4 model, Simon Brown A small, readable notation for diagrams.
  • Architecture decision records A one-page template and examples.
  • Fundamentals of Software Architecture, Richards and Ford A vocabulary for trade-offs and characteristics.
  • Software Architecture in Practice, Bass, Clements and Kazman The SEI treatment of quality attributes.

L8Collaboration and change over time50-70 hNot started

Software is written once and changed for years by people who were not there. Optimise for the reader and for the safety of the next change.

What you must know

Git as history
Commits are arguments about why. Rebase, bisect and blame are tools for reading that history.
Code review
Review for correctness, clarity and missing cases, not for style a formatter could settle.
Continuous integration
A change should be proven on every commit. Short-lived branches keep the proof cheap.
Trunk-based development
Small, frequent merges beat long-lived branches that grow conflicts and hide risk.
DORA findings
Lead time, deployment frequency, change failure rate and time to restore describe a team better than story points.
Documentation
Write what a newcomer cannot infer: decisions, invariants and how to run the thing.

Practice ladder

  1. Study one. Read a merged pull request and write down what the review changed and why.
  2. Finish one. A branch with a failing CI check. Diagnose it from the log and fix only the cause.
  3. Do one cold. Ship a small change to a real open source repository and carry it through review.

Build thisOne real merged pull request to an open source project, or a two-person project with review on every commit, CI on every push, a passing pipeline and a short onboarding README.

Gate, four questions

Answer from memory before opening any answer. Set a prediction first, then grade each question honestly.

  1. Why are small, frequent merges safer?

    Reveal the answer

    The diff is small, conflicts are rare, feedback is fast and a bad change is easy to identify and revert.

  2. What is git bisect for?

    Reveal the answer

    It binary-searches commit history to find the first commit that introduced a regression.

  3. What do the DORA measures tell you?

    Reveal the answer

    How fast and how safely a team delivers change, measured on outcomes rather than on estimates.

  4. What belongs in a code review?

    Reveal the answer

    Correctness, edge cases, clarity and design. Style belongs in a formatter.

Go deeper

  • Pro Git, Chacon and Straume Free. Read chapters 3 and 7 carefully.
  • Google engineering practices, code review Free, short, specific.
  • Accelerate, Forsgren, Humble and Kim, and DORA research The evidence behind the four measures.
  • Trunk-based development Patterns and their costs.
  • Software Engineering at Google, Winters, Manshreck and Wright Free. Read the chapters on time and change.

Judgment L9 to L10

L9Reliability, security and operations80-100 hNot started

Systems fail, and correctness includes behavior under failure, attack and load. You must be able to see what you shipped before you can claim it works.

What you must know

Observability
Logs, metrics and traces answer different questions. Instrument before the incident, not during it.
SLOs and error budgets
Set a target, measure against it, and let the budget decide when to stop shipping features.
Failure is normal
Timeouts, retries with jitter, idempotency keys and circuit breakers keep a partial failure local.
Threat modelling
List assets, entry points and trust boundaries before choosing controls.
Common vulnerabilities
Injection, broken access control, leaked secrets and unsafe deserialization. Check the OWASP ten by name.
Incidents
A blameless postmortem turns one failure into a change that prevents the class of failure.

Practice ladder

  1. Study one. Read a public postmortem and map the timeline, the trigger and the missing signal.
  2. Finish one. A service with a dashboard but no SLO. Define one, then add the alert that would have caught the incident.
  3. Do one cold. Inject a failure into your own service, detect it from your telemetry, and write the postmortem.

Build thisTake a service to a defined production state: dashboards, one SLO with an error budget, a runbook, a load test with a stated limit, a security review against the OWASP ten, a canary release, and a blameless postmortem from an injected failure.

Gate, four questions

Answer from memory before opening any answer. Set a prediction first, then grade each question honestly.

  1. Why set an SLO instead of aiming for 100 percent?

    Reveal the answer

    Perfect reliability is unaffordable and slows change; a budget makes the trade explicit and measurable.

  2. Why do retries need jitter and idempotency?

    Reveal the answer

    Synchronised retries amplify load, and a duplicate request must not apply a change twice.

  3. What is a trust boundary?

    Reveal the answer

    A point where data crosses between components with different privileges; it is where validation and authorisation belong.

  4. What makes a postmortem useful?

    Reveal the answer

    It identifies the systemic causes and produces concrete preventive work, without assigning blame to a person.

Go deeper

  • Site Reliability Engineering, Beyer et al. Free. Start with SLOs and incident response.
  • The Site Reliability Workbook Free, practical companion.
  • Release It!, Michael Nygard Stability patterns and the failure modes they address.
  • OWASP Top Ten The baseline list, with examples and fixes.
  • Security Engineering, Ross Anderson Free third edition. Read for the mental model.
  • The Tail at Scale, Dean and Barroso (2013) Why the slowest request defines the user’s wait.

L10Judgment and synthesis200 h and openNot started

Mastery is not knowing more. It is repeatedly making defensible decisions under uncertainty, and making other people’s decisions better too.

What you must know

Problem framing
Half of engineering is deciding what the problem is. Write the question before the answer.
Choosing what not to build
The cheapest, safest and most maintainable code is the code you did not write.
Primary sources
Papers, RFCs and postmortems beat summaries. Learn to find the claim and the evidence.
Cost and capacity models
Back-of-envelope arithmetic should decide architecture before a benchmark exists.
Teaching
Explain a topic without notes. The gaps in your explanation are the gaps in your model.
Calibrated uncertainty
Say what you know, what you assume and how you would find out. Being wrong clearly is a skill.

Practice ladder

  1. Study one. Read one systems paper and reconstruct its argument, assumptions and measurement in one page.
  2. Finish one. A design review with a proposal and missing trade-offs. Supply the objections yourself.
  3. Do one cold. Defend a technical decision to a skeptical reviewer using only evidence you can point to.

Build thisOne substantial original system you designed, built, operated, measured and documented over months, plus a written retrospective of the decisions you would change, and one topic you taught to someone else from memory.

Gate, four questions

Answer from memory before opening any answer. Set a prediction first, then grade each question honestly.

  1. Why is problem framing an engineering task?

    Reveal the answer

    The solution is judged against the stated problem; a precise, falsifiable problem statement prevents excellent work on the wrong thing.

  2. Why read the paper rather than the summary?

    Reveal the answer

    The assumptions, limitations and measurement conditions live in the original and decide whether the result applies to you.

  3. What does teaching reveal?

    Reveal the answer

    It forces retrieval and exposes missing links in your model that recognition hides.

  4. What does calibrated uncertainty sound like?

    Reveal the answer

    A claim, the confidence behind it, the assumption it rests on, and the experiment that would change your mind.

Go deeper

  • The Mythical Man-Month, Frederick Brooks Read No Silver Bullet and the essay on conceptual integrity.
  • How to Solve It, G. Polya A short method for attacking a problem you do not recognise.
  • The Art of Doing Science and Engineering, Richard Hamming On choosing problems worth doing.
  • Thinking in Systems, Donella Meadows Stocks, flows and feedback, for a system you cannot see whole.
  • MIT 6.5840 Distributed Systems Free labs built from the original papers.
  • Raft consensus A paper, a visualisation and a spec you can implement.
